# 淘宝生产级 Agent 深度笔记：为什么放弃 ReAct，转向 PES

---

## 一、系统背景：GrowBrain 是什么

GrowBrain 是淘宝内容生态的 **Agentic 内容成长引擎**，核心命题是：

> 将内容成长决策从"规则拍板 + 人工兜底"升级为 **Agent 驱动的智能决策**，同时保证生产链路要求的延迟、稳定性和可解释性。 

它直接参与"这条内容要不要流量扶持、给多少 PV、为什么"的最终决策，每天处理上万次请求。

---

## 二、为什么放弃 ReAct？两个致命问题

淘宝团队不是"理论上觉得 ReAct 不好"，而是**在生产环境踩了真实的坑**，才决定换架构。

### 问题一：ReAct + 小模型 = 幻觉失控

**场景**：用户请求"请帮我分析下内容A的潜力分"，系统注册了 `content_potential_tool`（调用潜力预估服务接口获取真实潜力分）。

**预期流程**：
```
第一次 LLM 调用 → 返回 function_call 要求调用 content_potential_tool
→ 框架执行工具拿到真实潜力分
→ 第二次 LLM 调用 → 基于真实数据返回最终结果
```

**实际翻车**：
> 当我们使用 Qwen3-0.6B 小模型时，ReactAgent 频繁翻车。小模型在 ReAct 循环的第一次 LLM 调用中，没有返回 `function_call`，而是直接输出了格式正确但数据全假的回答："潜力分 75 分，中等潜力，建议优化标题"。`content_potential_tool` 根本没有被调用过。 

**根因分析**：
- ReAct 模式下，LLM **同时承担"决策调度"和"内容生成"两个职责**
- 小模型容易被输出 Schema 的格式"带偏"：它一看到最终输出应该长什么样，就直接照着格式编一个，**跳过了中间的 Tool 调用**
- 高并发场景下，即使 5% 的幻觉率，每天上万次请求就意味着几百次假数据

**Prompt 强制指令无效**：
> 我们在 Prompt 里加了强制指令"必须先调用工具获取数据"，但小模型仍然有概率忽略。 

**结论**：**ReAct 不适用于小模型 + 高并发的工业落地场景。**

---

### 问题二：ReAct 的有状态设计 = 高并发隐患

ReAct 的循环执行需要维护一个"有状态的大而全的对象"：
- 对话历史（Memory）
- 当前步骤状态
- 工具调用结果
- 中间推理上下文

在分布式高并发场景下，用户的第 N 次请求可能路由到任何一台机器，那台机器需要能立即接续对话。这就涉及到：
- Session 的路由
- 上下文的持久化
- 快速恢复

**有状态设计让横向扩展变得极其困难。**

---

## 三、解法：PES 三段式架构（Planning + Execute + Summarize）

淘宝的解法不是"微调一下 ReAct"，而是**彻底重构架构**，把"想"和"做"在时序上分开。

### 3.1 PES 核心思想

| 阶段 | 职责 | LLM 角色 |
|------|------|---------|
| **Planning** | 把用户请求拆解成任务列表（DAG） | 只拆任务，不关心工具怎么调 |
| **Execute** | 框架按拓扑顺序执行工具调用 | **框架控制**，LLM 不参与 |
| **Summarize** | 基于执行结果生成最终回答 | 只做总结，不决策 |

**同样是"分析内容 A 的潜力分"：**
- Planning：LLM 输出 `[调用 content_potential_tool 获取潜力分]`
- Execute：框架**确定性**地调用工具，拿到真实数据
- Summarize：LLM 基于真实数据生成分析报告

---

### 3.2 ReAct vs PES 全维度对比

| 维度 | ReAct | PES |
|------|-------|-----|
| **控制权** | LLM 驱动循环，框架被动等待 | 框架控制流程，LLM 只在特定阶段工作 |
| **LLM 调用次数** | 每轮循环都要调用，N 个工具可能需要 2N+ 次 | Planning 1 次 + Execute N 次 + Summary 1 次，可控 |
| **可预测性** | LLM 可能"跑偏"，陷入无效循环 | 任务列表确定后严格执行，不会偏离 |
| **小模型适配** | 小模型在 ReAct 循环中容易出错、幻觉 | 每个阶段 prompt 更聚焦，小模型也能胜任 |
| **调试成本** | 多轮交互黑盒，难以定位问题出在哪一轮 | 三阶段清晰可追踪，每个任务独立记录 |
| **并发友好** | 单次请求占用时间长（多轮 LLM 调用） | 执行阶段任务间可并行，整体时延更低 |

> 综合上述缺点，我们考虑采用 PES 三段式这种更为稳定的 Agent 架构...使用该架构，执行阶段数量固定，每步任务明确，延迟可估、整体行为可控、并且每次请求决策全链路可回放。 

---

### 3.3 PES 的额外好处：解决"大量噪声引入"问题

在生产环境中，为了防止 LLM 跑偏，往往会在 Prompt 中注入大量指导性指令。但在 ReAct 模式下：

> 这些 prompt 在小模型推理阶段会成为 LLM 的噪声，LLM 无法聚焦在关键信息上。 

PES 把职责拆开，每个阶段的 Prompt 更聚焦：
- Planning 阶段只需要告诉模型"怎么拆任务"
- Summarize 阶段只需要告诉模型"怎么总结结果"
- 中间执行阶段完全不需要 LLM 参与

## 四、淘宝 Agent 的其他关键工程决策

### 4.1 Agent 矩阵分工：不用一个大模型端到端

淘宝不用一个大模型解决所有问题，而是拆成多个职责专一的子 Agent：

| 子 Agent | 职责 |
|---------|------|
| **潜力预估 Agent** | 分析新内容获流潜力 |
| **流量分配 Agent** | 流量投资决策（给不给、给多少、什么时候停） |
| **流量诊断 Agent** | 回溯分发日志，在推理链中完成获流诊断归因 |

> 子 Agent 各管各的，出问题能精确定位到环节和模型版本。 

---

### 4.2 双 Pipeline 物理隔离

```
┌─────────────────────────────────────────────────────────────┐
│                    能力底座（共享）                            │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐     │
│  │ Agent矩阵 │  │  Memory  │  │ Prompt管理│  │ AB框架   │     │
│  └──────────┘  └──────────┘  └──────────┘  └──────────┘     │
└─────────────────────────────────────────────────────────────┘
                              │
              ┌───────────────┴───────────────┐
              │                               │
              v                               v
    ┌──────────────────┐          ┌──────────────────┐
    │ SystemPipeline   │          │  ChatPipeline    │
    │ （线上中控）      │          │ （对话场景）      │
    │                  │          │                  │
    │ • 批量高并发      │          │ • 自然语言输入    │
    │ • 规则驱动编排    │          │ • LLM动态编排    │
    │ • 严格schema输出  │          │ • 多轮上下文     │
    │ • 关心吞吐和SLA   │          │                  │
    └──────────────────┘          └──────────────────┘
```

- **SystemPipeline**：服务线上中控，批量高并发、规则驱动编排、严格 schema 输出
- **ChatPipeline**：服务产运和算法同学的对话需求，自然语言输入、LLM 动态编排执行图、多轮上下文
- 两条 Pipeline **共享同一套 Agent 矩阵和底层能力**，能力新增一次，两条线同时受益

---

### 4.3 决策可解释性白盒化

Agent 天然输出思考链和决策理由，"为什么给这个数"是决策过程本身的附属产物，不再需要额外挂一个解释模块。

**流量诊断 Agent 的核心优势**：
- 结构化输入，推理链白盒化
- 规则信号兜底 + LLM 语义分析：数据异常前置到数据处理阶段，LLM 只在规则之上做基于事实的 CoT 推理
- 诊断口径与策略口径同源，"诊断结论"可直接回流到下一轮投放决策，形成"投放→诊断→反馈"闭环

---

### 4.4 小模型生产可靠性工程

淘宝的核心经验：**经过 SFT 的小模型也可以稳定在线 Serving。**

关键做法：
- PES 架构让每个阶段 Prompt 更聚焦，降低小模型的推理负担
- 规则信号前置到数据处理阶段，LLM 只做基于事实的 CoT 推理
- 避免让小模型同时承担"决策调度"和"内容生成"两个职责

---

## 五、淘宝商品域 Agent 的另一种实践（补充）

除了 GrowBrain，淘宝商品域也有独立的 Agent 实践，走的是另一条路：

### 5.1 事件驱动的 Function-Centric Agent 架构

> 相较于引入功能完备但复杂 Agent 框架或者试图在 Java 领域复刻一个完整的平台级框架，我们只希望拥有一个"恰好够用"但又不会带来太多负担的 SDK。 

核心设计：
- **事件驱动**：通过商品领域事件触发 Agent 执行
- **Function-Centric**：以 Function 为核心原子能力，支持并行化与分片处理
- **Workflow 编排**：根据负载动态调整批量处理的并发度与吞吐量

### 5.2 部署架构

| 分组 | 职责 |
|------|------|
| **SKU 引擎分组** | 商品信息转换映射成 SKU 粒度，完成有无 SKU、item 和 SKU 状态以及属性文本等逻辑处理 |
| **LLM 分组** | 承担基于不同业务场景的大模型实时推理核心职能，动态调度多类型 Agent 数据生产链路 |
| **服务分组** | 读写分离 + 单元化架构：写服务以张北中心为唯一写入节点；读服务按单元化流量部署，通过 Tair 分布式缓存实现低延迟访问 |

### 5.3 AI 生产数据质量评测体系

> 基于 agent 应用，构建一套可量化、可归因、可复现的属性摘要大模型自动化评测系统。 

- 新桶 vs 老桶召回属性商品的数量、排名等信息的 AB 对比评测
- 利用大模型进行语义理解与打分，构建多维度规则体系（V 值准确性、完整性、可读性、一致性）
- 运营可以针对单品或线上 badcase 进行定向实时评测

## 六、面试核心考点提炼

### 高频追问 1：为什么 ReAct 不适合生产级？

**答三点**：
1. **幻觉不可控**：小模型在 ReAct 循环中容易跳过工具调用直接编数据，Prompt 强制指令也拦不住
2. **有状态设计阻碍扩展**：ReAct 需要维护对话历史、当前步骤状态等，分布式高并发下 session 路由和上下文恢复极其困难
3. **LLM 调用次数不可控**：N 个工具可能需要 2N+ 次 LLM 调用，延迟和成本不可预测

### 高频追问 2：PES 解决了什么问题？

**答三点**：
1. **职责分离**：Planning 只拆任务、Execute 框架确定性执行、Summarize 只总结，LLM 不再同时承担决策和执行
2. **行为可控**：任务列表确定后严格执行，不会偏离，执行阶段数量固定，延迟可估
3. **小模型友好**：每个阶段 Prompt 更聚焦，小模型也能稳定工作，降低推理成本

### 高频追问 3：双 Pipeline 设计的目的是什么？

**答**：SystemPipeline 服务线上高并发场景（规则驱动、严格 schema、关心吞吐和 SLA），ChatPipeline 服务对话场景（自然语言、动态编排、多轮上下文）。两条线共享能力底座，避免重复建设，同时物理隔离保证线上稳定性不受对话场景影响。

### 高频追问 4：Agent 可解释性怎么实现？

**答**：PES 架构天然白盒化——Planning 输出任务列表、Execute 输出工具调用结果、Summarize 输出推理链。不需要额外挂解释模块，"为什么给这个数"就是决策过程的附属产物。

# 生产级 Agent 架构演进深度笔记（多公司案例）

## 一、Octomind：放弃 LangChain，转向"模块化构建块"

### 1.1 背景

Octomind 是一家做 AI 测试自动化的公司，用多个 LLM 的 AI Agent 来自动创建和修复 Playwright 端到端测试。他们在生产中使用 LangChain **超过 12 个月**（2023 年初到 2024 年），最终彻底移除。 

### 1.2 为什么放弃 LangChain？

**核心问题：过度抽象和嵌套抽象，从生产力工具变成了阻碍。**

| 问题                    | 具体表现                                                     |
| ----------------------- | ------------------------------------------------------------ |
| **徒增复杂度**          | 翻译英语到意大利语，用原生 OpenAI API 几行代码搞定，LangChain 要引入 Prompt 模板、输出解析器、Chains 三个新抽象 |
| **限制架构演进**        | 需要从"单顺序 Agent"演进为"多专业 Agent 交互"时，LangChain 的抽象层成了限制因素 |
| **无法观察 Agent 状态** | 需要根据业务逻辑和 LLM 输出动态调整工具可用性，但 LangChain 不提供从外部观察 Agent 状态的方法 |
| **嵌套抽象**            | 改一个微小细节要穿透 5 层抽象，出问题排查困难                |

**关键判断**：一旦删除了 LangChain，"我们就不再需要将我们的需求转化为适合 LangChain 的解决方案。我们只需编写代码即可。" 

### 1.3 替代方案：模块化构建块（Building Blocks）

- 保留 LangChain 中**真正有用的组件**（如向量检索、特定工具封装）
- 用**简洁的底层代码 + 精心挑选的外部依赖包**替代框架级抽象
- 核心组件有限：字符串处理、API 调用、循环、向量 DB，不需要框架来管理这些基础操作

### 1.4 国内团队的共鸣

> "我在过去三个半月的实习时间里建立了一个 RAG agent。公司里的每个人都问我为什么不用 LangChain...我一直告诉他们，如果你有一个标准的用例，它会工作得很好，但如果你需要一些原创的东西，你必须经历 5 层抽象，只是为了改变一个微小的细节。此外，你不会真正理解流程中的每一步，所以如果出现任何问题或者你需要改进流程，你将从头开始。" 

**面试考点**：LangChain 适合 Demo 和标准化场景，大型/企业级项目建议自研轻量级框架，以适配微服务架构和现有基建。

## 二、字节跳动 DeerFlow 2.0：18 层中间件 + Sub-Agent 并发架构

### 2.1 定位

DeerFlow 是字节跳动开源的**超级智能体执行底座**，支撑了内部飞书、抖音电商、客服等上百个 Agent 场景的落地。经历了从 1.0 到 2.0 的彻底重构。 

### 2.2 核心架构：18 层中间件流水线

DeerFlow 2.0 的 Lead Agent 采用了**严格的中间件链式架构**，共 18 个中间件按序执行，每个中间件只处理一个横切关注点，通过 `before`/`after` 钩子实现 AOP 式编程。 

```
1.  ThreadDataMiddleware      # 创建线程隔离目录
2.  UploadsMiddleware         # 注入上传文件
3.  SandboxMiddleware         # 获取沙箱环境
4.  DanglingToolCallMiddleware    # 处理中断工具调用
5.  LLMErrorHandlingMiddleware    # 错误规范化
6.  GuardrailMiddleware       # 安全策略检查
7.  SandboxAuditMiddleware    # 沙箱审计日志
8.  ToolErrorHandlingMiddleware   # 工具错误恢复
9.  SummarizationMiddleware   # 上下文摘要
10. TodoListMiddleware       # 任务追踪（Plan Mode）
11. TokenUsageMiddleware     # Token 用量记录
12. TitleMiddleware          # 自动生成标题
13. MemoryMiddleware         # 记忆提取队列
14. ViewImageMiddleware      # 图像注入（多模态）
15. DeferredToolFilterMiddleware  # 延迟工具过滤
16. SubagentLimitMiddleware  # 子 Agent 并发限制
17. LoopDetectionMiddleware  # 循环检测
18. ClarificationMiddleware  # 澄清请求拦截
```

### 2.3 Sub-Agent 并发架构

DeerFlow 最强大的能力是**动态生成 sub-agents**，并行执行任务分解：

- **双线程池设计**：调度池（3 workers）+ 执行池（3 workers）
- **最大并发**：3 个子 Agent
- **超时**：15 分钟
- **隔离上下文**：每个 sub-agent 有独立的上下文，互不干扰

**执行流程**：
```
Lead Agent 调用 task() 工具
       ↓
SubagentExecutor 调度
       ↓
后台线程执行子 Agent
       ↓
5秒轮询 + SSE 事件流
       ↓
返回结构化结果
```

**实际场景**：要求"研究 2025 年 AI Agent 领域的 5 个主要框架并生成对比报告" → 分解为 5 个 sub-agent 并行研究 → Lead Agent 汇总 → 输出结构化报告。 

### 2.4 记忆系统：LLM 驱动的长期记忆

**数据结构**（存储于 `memory.json`）：

```json
{
  "userContext": {
    "workContext": "...",
    "personalContext": "...",
    "topOfMind": "1-3句话摘要"
  },
  "history": {
    "recentMonths": [],
    "earlierContext": [],
    "longTermBackground": []
  },
  "facts": [
    {
      "id": "uuid",
      "content": "用户偏好...",
      "category": "preference/knowledge/context/behavior/goal",
      "confidence": 0.85,
      "createdAt": "2026-01-01T00:00:00Z",
      "source": "conversation"
    }
  ]
}
```

**工作流程**：
1. `MemoryMiddleware` 过滤消息（用户输入 + AI 回复）
2. 防抖队列（默认 30s）批量处理
3. 后台线程调用 LLM 提取事实
4. 原子写入（临时文件 + rename）
5. 下次对话注入 Top 15 事实 

### 2.5 安全与沙箱

- **Docker 沙箱**：AI 在隔离容器中读写文件、执行 Bash、运行长耗时代码
- **多级沙箱**：LocalSandbox（本地，默认禁用 bash）/ DockerSandbox（推荐生产用）
- **Guardrail 中间件**：安全策略检查
- **审计日志**：完整记录沙箱操作

**生产部署必须**：IP 白名单、反向代理 + 强认证、VLAN 网络隔离、禁用 LocalSandbox 的 bash 执行。

### 3.1 背景

### 3.3 可观测 AI Agent（稳定性工程）

小红书可观测团队负责人王亚普在 QCon 分享了**大模型时代的稳定性工程实践**： 

**AI Infra 观测挑战**：
- 内部训练框架多元、GPU 品牌参数与型号参差不齐
- 千卡甚至万卡集群训练时，任务 Hang 住所有 Pod 表现都是卡死，故障种类多且定位复杂
- AI 应用的全链路追踪对现有基建存在很多兼容性挑战

**可观测 AI Agent 架构设计**：
- 围绕稳定性工程的 AI + 建设思路
- 融合传统 AIOps 能力与大模型的落地实践
- GPU 故障诊断、训练 Hang 故障发现与自动化诊断

### 3.4 记忆系统设计（面试高频）

小红书大模型二面真题：记忆模块设计采用**三层架构**： 

| 层级 | 名称       | 存储                        | 策略                                                         |
| ---- | ---------- | --------------------------- | ------------------------------------------------------------ |
| L1   | 工作记忆层 | Context Window              | 保留最近 3-5 轮原始对话，更早历史做摘要压缩；多步推理时维护结构化 task_state |
| L2   | 近期记忆层 | Redis                       | 当前会话完整历史 + 近 7 天高频记忆；sorted set 按时间排序，支持范围查询 |
| L3   | 长期记忆层 | 向量库 + PostgreSQL + Neo4j | 语义记忆走 embedding 检索；结构化数据走精确查询；复杂实体关系走知识图谱 |

**数据流向**：任务执行中的重要信息从 L1 → L2 → L3 逐层沉淀；新任务开始时从 L3 检索相关记忆加载到 L1。

**三维评分检索**（借鉴 Generative Agents）：
- **Recency（时近性）**：最近发生的记忆权重高
- **Relevance（相关性）**：语义匹配度
- **Importance（重要性）**：固有重要性

权重可按业务场景调：客服场景 recency 权重高，知识问答场景 relevance 权重高。

## 四、腾讯：ClawPro / OpenClaw 企业级 Agent 架构

### 4.1 核心定位

腾讯云 AI Agent 已在多业务场景中完成闭环验证，核心引擎是 **ClawPro**（Agent 工作流引擎）。 

### 4.2 真实落地案例

| 行业          | 场景                                           | 效果                                                         |
| ------------- | ---------------------------------------------- | ------------------------------------------------------------ |
| **财税 SaaS** | 海量票据处理，传统规则引擎无法处理不确定性任务 | 动态工具调用 + 多租户 Token 限流，实现 **24 小时全天候自动驱动** |
| **快消行业**  | 门店巡检多系统登记繁琐                         | 自然语义录入 → 打通内部计算与大数据平台 → 自动化运转         |
| **家政行业**  | 阿姨与客户的动态标签体系                       | RAG 技能 + Autopilot 模块多维度协同检索，派单决策周期从**"天"级缩短至"秒"级** |
| **游戏出海**  | 全球渠道运营                                   | **3-5 人团队覆盖 22 个海外渠道**，7×24 小时自动化数据采集与广告素材生成 |

### 4.3 企业级 Agent 构建路径

腾讯云提出的**从原型到生产的三阶段路径**： 

**阶段一：知识就位**
- 构建 RAG 知识库，解决"Agent 不知道什么"的问题

**阶段二：工作流编排（意图 + 执行）**
- **全局意图识别**：理解整个对话中的用户意图，而不仅仅是最新消息
  - 例：用户说"把时间改成晚上 7 点，不要 6 点了" → 识别为**修改现有预订**，而非新请求
- **长期记忆**：跨会话记住用户偏好（房型、饮食限制、会员状态）
- **关键工作流节点**：
  - 参数提取器：从自然语言提取结构化数据
  - LLM 意图识别：带推理的意图分类
  - 知识检索：从 RAG 获取相关上下文
  - 代码节点：执行自定义逻辑（价格计算、API 调用）
  - 条件分支：基于提取参数路由（VIP vs 普通客户）

**阶段三：评估驱动开发（EDD）**
- 思维链深度限制与兜底机制：设置最大循环次数与超时熔断
- 闭环测试集构建：收集 Bad Case，构建自动化评估基准
- LLM-as-a-Judge：对线上 Agent 输出在相关性、准确性、逻辑性维度多维度打分
- 状态管理工程化：结合 Redis 等外部缓存，确保分布式部署下的记忆一致性

## 五、国内团队：放弃 LangChain 的通用规律

### 5.1 为什么大型项目最终都走向自研？

多个独立来源的共识： 

| 维度         | LangChain 的问题                               | 自研的优势               |
| ------------ | ---------------------------------------------- | ------------------------ |
| **架构适配** | 单体应用设计，模块耦合度高，硬拆微服务改造量大 | 灵活适配现有微服务架构   |
| **运维体系** | 内置日志和监控逻辑与公司现有运维体系不兼容     | 深度集成公司基建         |
| **可控性**   | 发展路线图、API 变更、支持优先级不由团队掌控   | 完全自主，无被动升级风险 |
| **抽象层级** | 过度抽象，改一个小细节要穿透多层               | 按需抽象，代码透明可控   |

### 5.2 框架取舍原则

| 项目规模      | 建议方案                                         |
| ------------- | ------------------------------------------------ |
| 小项目 / Demo | 直接用原生 API，灵活无依赖                       |
| 中型 / 赶工期 | 可用 LangChain 快速搭骨架，但需警惕后期维护成本  |
| 大型 / 企业级 | **强烈建议自研框架**，以适配微服务架构和现有基建 |

## 六、面试核心考点速记

### 高频追问 1：为什么大厂最终都放弃 LangChain？

**答三点**：
1. **过度抽象限制创新**：改一个小细节要穿透多层抽象，不理解流程每一步，出问题只能从头开始
2. **架构不匹配**：LangChain 偏向单体应用，模块耦合度高，与企业微服务架构冲突
3. **失控风险**：发展路线、API 变更、社区生态不由团队掌控，被动升级产生技术债

### 高频追问 2：DeerFlow 的 18 层中间件设计哲学是什么？

**答**：每个中间件只处理一个横切关注点，通过 `before`/`after` 钩子实现 AOP 式编程。好处是：
- 职责单一，调试时定位问题精确到某一中间件
- 可插拔，按需启用/禁用特定中间件
- 生产级安全：Guardrail、SandboxAudit、LoopDetection 等安全中间件内嵌

### 高频追问 3：Sub-Agent 并发怎么设计？

**答**：双线程池（调度池 + 执行池），Lead Agent 调用 `task()` 工具 → SubagentExecutor 调度 → 后台线程执行 → 5 秒轮询 + SSE 事件流返回结果。每个 sub-agent 独立上下文，互不干扰，最大并发 3 个，超时 15 分钟。

### 高频追问 4：小红书三层记忆架构的检索策略？

**答**：三维评分——Recency（时近性）、Relevance（相关性）、Importance（重要性）。不是单纯找最相似的，而是综合加权。权重按业务场景调：客服 recency 高，知识问答 relevance 高。检索时从 L3 向量库 + 关系库召回，加载到 L1 Context Window。

### 高频追问 5：腾讯云提出的 EDD（评估驱动开发）是什么？

**答**：Enterprise Agent 不是功能做完就上线，必须：
1. 设置最大循环次数与超时熔断，防止死循环
2. 收集 Bad Case 构建闭环测试集
3. 用 LLM-as-a-Judge 对输出做多维度打分
4. 状态管理外置到 Redis，保证分布式一致性
