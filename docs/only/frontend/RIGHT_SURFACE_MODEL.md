### 提炼出的两个连续谱

1. **对话为主 ↔ 工作区为主**:Claude/v0 在左端(对话是控制面),Bolt/Cursor 在右端(工作区是控制面)
2. **固定槽位 ↔ 按需出现**:YouMind 固定三槽;Claude 按需展开;ChatGPT 正在从"按需面板"退向"流内嵌入"

## 2. DialogMesh 的位置:双槽位 + 表面可交换

用户判断正确——我们确实在中间。形式化为:

### 模型

**窗口 = 导航栏 + 两个内容槽位(主表面 + 副表面)。**
- 每个槽位可以承载一种**表面(Surface)**:对话 / 上下文 / 画布(图谱·任务图·瀑布) / 详情(节点·会话·产物)
- **副表面永远是主表面的"注释者与操作台"**,不是平行陈列的仪表盘
- 副表面:一次一个表面(多个候选用 tab 切换,不堆叠)、可与主表面交换(⇄)、可整个收起

### 默认配对(路由给默认,用户可覆盖)

| 页面 | 主表面 | 副表面 | 对应业界先例 |
|---|---|---|---|
| 聊天 | 对话 | **上下文工作台**(当前会话注入了什么/画像摘要) | Claude split pane |
| 图谱 / 任务 / 深层链 | 画布 | 对话(就这张图讨论) | Bolt/Cursor 倒置 |
| 会话 | 列表 | 详情(选中 session 的摘要与状态) | Linear master-detail |
| 画像/元认知/行为 | 洞察报告 | 原始数据(字段级) | — |
| 工程/网关/管道 | 监控面板 | 无(单槽全宽) | — |

### 上下文副表面:从"陈列"改成"可操作"

这是"中间对话右边调整上下文"的落地 —— 恰好就是 ContextCompiler 的 UI 化:

- 记忆卡片带操作:**钉住**(注入下轮)/ **本轮移除** / 查看来源对话
- 顶部一条"上下文构成"概要:本轮注入 N 条记忆 + 子图 X 个节点,点开看编译明细(瀑布的入口)
- 画像/状态数据(82%、63/52/50)**不占副槽**:降为顶栏或侧栏状态点,点开弹层看详情;完整版归画像页自己当主表面

## 3. 现在的右栏为什么"凌乱"——三条根因

1. **五种异质内容堆在一个 300px 槽里**(状态条/数字瓦片/记忆卡/迷你图/按钮),视觉重量相近、没有主角 → 修法:一次一个表面,tab 切换
2. **监控面板思维而非工作表面思维**:所有内容都是被动陈列,没有一个可操作的控件 → 修法:记忆卡加钉住/移除,数据变操作对象
3. **与主表面无角色分工**:中间在讲故事,右栏在播仪表,二者不互相解释 → 修法:副表面内容必须回答"主表面此刻正在发生什么"(Claude 的 thread/pane 关系)

## 6. 追加:槽位主权交给用户(2026-08-15,用户拍板的方向)

> 用户原话:"问题在于这个非固定吧?后面有 UI 自动化,中间屏幕就像虚拟机一样被操作,右边就变成对话了——把副屏幕的选择给用户是最好的。"

### 原则升级:槽位与表面解耦

第 2 节的"默认配对表"降级为**默认建议**。真正的规则是:

- **槽位是空的容器,表面是可寻址的对象**。用户可以把任何表面放进副槽(或交换到主槽),路由只负责给一个合理的初始配对
- 配对按会话/项目**持久化**(下次进来还是你调好的布局)
- 副槽头部必须有一个**表面切换器**(下拉或 tab):对话 / 上下文 / 画布 / 详情 / 自动化视口…

### UI 自动化场景验证了"非固定"的必要性

自动化(agent 操作界面)场景下:主槽 = **自动化视口**(被操作的画面,像看一台虚拟机),副槽 = 对话(你指挥它/它汇报)。
这个配对在第 2 节的静态表里根本不存在——它是运行时由任务类型决定的。如果槽位内容写死在路由里,这个场景就装不进去。

### 对前端架构的推论(记录备查)

- 表面必须实现为**自包含组件**(自己的数据契约,不依赖路由上下文),才能被任意槽位装载
- 槽位状态放**布局 store**(如 zustand),不放路由;路由只带 `?companion=context` 这类浅参数用于分享链接
- agent 与用户**平权**:自动化引擎也走同一个"绑定表面到槽位"的接口,不开后门

## 7. 与「项目维度」的关系(见 PROJECT_DIMENSION.md)

项目是**范围容器**(决定表面里装什么数据),槽位是**布局容器**(决定表面摆在哪)。两者正交:切换项目 = 所有表面的数据范围一起换;切换槽位 = 布局换,数据范围不变。
