## 修正声明（从 v5.0 到 v5.1）

| v5.0 问题 | v5.1 修正方向 |
|-----------|--------------|
| 节点只有单一 `knowledge_level`（L1-L6） | 节点支持**多视角**（perspective），每个视角有独立的层级和约束上下文 |
| 误匹配后无法修正（如未知论文匹配到 FPGA） | 发散网络解构后，**约束规则**自动检测误匹配并推荐修正 |
| 层级与发散网络独立运行 | **双网络协调**：层级验证发散结果，发散修正层级归属 |
| 内容只能隶属一个层级 | 内容可以同时隶属 L1-L3，取决于**约束关系** |
| 发散网络只是生成启发式节点 | 发散网络负责**解构子模块**、**模糊关联**、**约束修正** |

## 1. 问题陈述

### 1.1 v5.0 的误匹配问题

v5.0 的 Claw 模式测试中出现第 6 篇论文（未知领域）被误匹配到 FPGA 模板。根因：

> **节点只能有一个层级。** 但现实中一个概念（如"热传导"）同时是：
> - L1 物理现象（热量自发流动）
> - L2 数学方程（∂T/∂t = α∇²T）
> - L3 算法实现（有限差分数值求解）
> - L4 系统架构（热-机耦合系统）

**具体症状：**

| 症状 | 根因 | 举例 |
|------|------|------|
| 未知论文误匹配到 FPGA | 关键词匹配无多视角验证 | "A Novel Approach" 无特征词，但 FPGA 模板被默认选择 |
| 牛顿定律被标记为 L3（算法） | 人工标注错误，无自动校验 | "Newton's Second Law" 的核心是物理定律，不是算法 |
| 热传导只能选 L1 或 L2 | 单一层级限制 | 无法同时表达"物理现象+数学方程+数值算法" |
| 发散与层级网络独立运行 | 无双向协调机制 | 发散解构的子模块可能跨越多个层级，但层级网络无法验证 |

### 1.2 核心目标

将系统从**单网络**升级为**双网络协调**：

1. **多视角层级归属**：一个节点可以有多个视角（perspective），每个视角对应一个层级和约束上下文
2. **发散网络解构**：从节点出发，解构出子模块、模糊关联、约束修正建议
3. **双网络协调**：层级网络验证发散结果的结构合理性，发散网络修正层级网络的误匹配
4. **约束驱动的层级判定**：层级归属不是固定的，而是取决于约束关系

## 2. 核心架构：双网络协调

### 2.1 双网络结构

```
┌─────────────────────────────────────────────────────────────────┐
│                    应用层 (API / UI / Pipeline)                  │
├─────────────────────────────────────────────────────────────────┤
│                    协调层 (Coordination Engine)                    │
│  ┌─────────────────────┐    ┌─────────────────────┐             │
│  │ 层级网络 (Convergent)│ ↔ │ 发散网络 (Divergent)│             │
│  │                     │    │                     │             │
│  │ • 六层结构验证       │    │ • 子模块解构         │             │
│  │ • 约束规则校验       │    │ • 模糊关联发现       │             │
│  │ • 多视角管理         │    │ • 误匹配修正建议     │             │
│  │ • 视角验证           │    │ • 约束上下文检测     │             │
│  └─────────────────────┘    └─────────────────────┘             │
│              ↑                        ↑                          │
│         validate                 deconstruct                    │
│              ↓                        ↓                          │
│         ┌─────────┐              ┌─────────┐                     │
│         │ nodes_v2│              │submodules│                    │
│         │perspectives            │associations│                   │
│         │validation              │corrections │                   │
│         └─────────┘              └─────────┘                     │
└─────────────────────────────────────────────────────────────────┘
```

**协调流程：**

```
Step 1: 层级网络创建节点（带默认视角）
    ↓
Step 2: 发散网络解构节点 → 提取子模块、关联、约束修正
    ↓
Step 3: 层级网络验证发散结果
    - 子模块的层级是否在合理范围？
    - 关联的语义是否符合六层结构？
    - 约束修正是否触发新视角？
    ↓
Step 4: 如果验证通过 → 吸收发散结果（添加视角/边）
    如果验证失败 → 标记为"待人工协调"
    ↓
Step 5: 用户查询时，根据约束上下文选择最佳视角
```

### 2.2 多视角层级归属

**核心概念**：节点不是单一层级，而是**视角集合**。

```yaml
id: heat-conduction
type: concept

perspectives:
  - name: physical
    level: L1
    constraint_context: "自然现象 / 不可逆过程"
    what: "热自发从高温流向低温，通过分子振动传递能量"
    why_exists: "热力学第二定律：孤立系统熵增"
    physical_basis: ["second-law-thermodynamics", "molecular-vibration"]
    confidence: 1.0
    is_default: true

  - name: mathematical
    level: L2
    constraint_context: "偏微分方程 / 解析解"
    what: "傅里叶热传导方程，描述温度场演化"
    why_exists: "需要量化热传递以进行工程设计"
    mathematical_form: "∂T/∂t = α∇²T; α = k/(ρc_p)"
    physical_basis: ["fourier-law"]
    confidence: 0.95

  - name: algorithmic
    level: L3
    constraint_context: "数值求解 / 有限差分"
    what: "有限差分或有限元方法数值求解热方程"
    why_exists: "解析解仅适用于简单几何；实际问题需要数值方法"
    engineering_mapping: ["finite-element-method", "cfd"]
    confidence: 0.85

  - name: system
    level: L4
    constraint_context: "热-机耦合系统"
    what: "机床结构中的热-力耦合变形系统"
    why_exists: "热变形导致加工误差，需要系统级补偿"
    failure_modes: ["非均匀温度分布", "热惯性延迟"]
    confidence: 0.80
```

**关键设计：**
- 一个节点可以有任意数量的视角
- 每个视角有独立的 `confidence` 和 `constraint_context`
- 默认视角用于无约束查询，但约束上下文可以切换视角
- 视角之间可以互相验证（如 `mathematical` 视角验证 `physical` 视角的公式一致性）

### 2.3 发散网络解构

发散网络从节点出发，执行三项任务：

#### 2.3.1 子模块解构

将大概念分解为小组件：

```
"热传导" → 子模块：
├── temperature-gradient     (L1) — 温度梯度引起的热应力
├── boundary-condition       (L2) — 边界条件对热传导的影响
├── thermal-inertia          (L1) — 热惯性导致的响应延迟
├── sensor-placement         (L5) — 温度传感器布局优化
├── finite-difference-grid   (L3) — 有限差分网格划分
└── convergence-criterion    (L6) — 数值收敛判据
```

**子模块的层级检测**：如果子模块跨越多个层级，建议添加多视角。

#### 2.3.2 模糊关联

发现与相关/相似概念的非精确关联：

```
"热传导" → 模糊关联：
├── thermal-deformation      (causes, strength=0.95)
├── pinn                     (modeled_by, strength=0.80)
├── heat-transfer-equation   (governed_by, strength=0.95)
├── fourier-law              (grounded_in, strength=0.90)
└── thermal-expansion        (related_to, strength=0.85)
```

**关联强度**：基于文本共现、关键词重叠、层级距离计算。

#### 2.3.3 约束修正

基于约束规则检测误匹配：

| 规则 | 触发条件 | 修正动作 | 示例 |
|------|---------|---------|------|
| physical_phenomenon_override | 文本含"现象/定律/原理/公理" | 添加 physical 视角 (L1) | 牛顿定律误标为 L3 → 修正为 L1 |
| mathematical_derivation_override | 文本含"推导/定理/证明/公式" | 添加 mathematical 视角 (L2) | 傅里叶级数误标为 L3 → 修正为 L2 |
| hardware_implementation_override | 文本含"硬件/FPGA/实现/部署" | 添加 engineering 视角 (L5) | 算法论文误标为 L3 → 添加 L5 |
| validation_focus_override | 文本含"验证/测试/收敛/证明" | 添加 validation 视角 (L6) | 系统设计论文含大量验证 → 添加 L6 |

### 4.2 发散网络（Divergent）

新增三个核心功能：

```python
class DivergentDeconstructor:
    def deconstruct(self, node_id: str) -> DeconstructionResult:
        """解构节点，返回子模块、关联和修正建议。"""
        
        # 1. 匹配模板
        template_id = match_template(node.title + node.content)
        
        # 2. 提取子模块
        submodules = extract_submodules(template_id, text)
        
        # 3. 提取模糊关联
        associations = extract_associations(template_id, text)
        
        # 4. 约束修正检测
        corrections = check_constraints(text, node_id)
        
        # 5. 判断是否多视角
        multi_perspective = len(corrections) > 1 or len(submodules) > 3
        
        return {
            "submodules": submodules,
            "associations": associations,
            "corrections": corrections,
            "multi_perspective": multi_perspective,
        }
    
    def coordinate_with_convergent(self, node_id: str) -> CoordinationResult:
        """与层级网络协调。"""
        
        # 1. 发散解构
        divergent_result = self.deconstruct(node_id)
        
        # 2. 获取层级网络的默认视角
        default_perspective = store.get_default_perspective(node_id)
        
        # 3. 检查一致性
        actions = []
        for corr in divergent_result.corrections:
            if corr.suggested_level != default_perspective.level:
                actions.append({
                    "type": "add_perspective",
                    "perspective_name": corr.suggested_perspective,
                    "level": corr.suggested_level,
                    "reason": corr.reason,
                })
        
        # 4. 如果子模块跨越多个层级，建议多视角
        if divergent_result.multi_perspective:
            levels = set(sm.level for sm in divergent_result.submodules)
            if len(levels) > 1:
                actions.append({
                    "type": "multi_perspective_suggested",
                    "detected_levels": sorted(levels),
                })
        
        return {
            "divergent_result": divergent_result,
            "convergent_perspective": default_perspective,
            "coordination_actions": actions,
        }
```

### 4.3 协调验证流程

```
输入：新节点（带默认视角）

Step 1: 层级网络创建节点
  ├── 添加默认视角（如 L3）
  └── 设置 constraint_context

Step 2: 发散网络解构
  ├── 提取子模块（检查是否跨越层级）
  ├── 提取模糊关联（检查语义一致性）
  └── 约束修正检测（检查是否误匹配）

Step 3: 层级网络验证
  ├── 验证子模块层级是否在合理范围
  ├── 验证关联的语义是否符合六层结构
  └── 验证约束修正是否触发新视角

Step 4: 决策
  ├── 如果全部验证通过 → 吸收发散结果（添加视角/边）
  ├── 如果部分验证失败 → 标记"待人工协调"
  └── 如果全部验证失败 → 拒绝发散结果，保留原视角

Step 5: 用户查询
  ├── 无约束查询 → 使用默认视角
  ├── 有约束查询 → 根据 constraint_context 选择视角
  └── 多视角查询 → 返回所有视角并标注置信度
```

## 6. 关键设计决策

### 6.1 为什么必须多视角？

| 场景 | 单视角问题 | 多视角解决 |
|------|-----------|----------|
| "热传导" | 只能选 L1 或 L2 | 同时有 physical(L1) + mathematical(L2) + algorithmic(L3) |
| "牛顿定律" | 被误标为 L3（算法） | 物理视角(L1) 修正误匹配，算法视角(L3) 保留应用层面 |
| "FxLMS" | 只能 L3（算法） | 添加 L1（延迟物理）+ L5（FPGA实现）+ L6（收敛证明） |
| 用户查询 | 返回固定层级 | 根据约束上下文返回最合适的视角 |

### 6.2 双网络 vs 单网络

| 维度 | 单网络（v5.0） | 双网络（v5.1） |
|------|---------------|---------------|
| 误匹配处理 | 人工修正 | 发散网络自动检测 + 层级网络验证 |
| 多层级归属 | 不支持 | 多视角支持 |
| 子模块发现 | 人工填充 | 发散网络自动解构 |
| 模糊关联 | 无 | 基于关键词模板的关联发现 |
| 约束上下文 | 无 | 每个视角有独立约束 |
| 验证机制 | 无 | 双向验证（发散→层级，层级→发散） |

### 6.3 约束修正 vs 固定层级

| 固定层级 | 约束修正 |
|----------|---------|
| 节点创建时确定层级 | 节点创建时只设默认视角 |
| 一旦确定不可更改 | 发散网络持续检测修正 |
| 人工标注错误无法发现 | 约束规则自动检测误匹配 |
| 内容跨越层级时冲突 | 多视角同时存在，无冲突 |

- `knowledge_level` 字段继续可用（作为单视角的简化表示）
- v5.0 的 `explain_why()` / `explain_how()` 继续可用
- 新增 `node_perspectives` 表是扩展，不影响旧数据

### 7.2 迁移路径

```sql
-- 从单视角迁移到多视角
-- 将 nodes_v2.knowledge_level 迁移为默认视角
INSERT INTO node_perspectives (id, node_id, perspective_name, knowledge_level, is_default, what)
SELECT 
    'persp::' || id || '::core',
    id,
    'core',
    knowledge_level,
    1,
    what
FROM nodes_v2 
WHERE knowledge_level IS NOT NULL;
```

### 7.3 降级策略

- 如果 `node_perspectives` 表为空，回退到 `nodes_v2.knowledge_level`
- 如果发散网络不可用，层级网络独立运行（v5.0 行为）
- 如果协调引擎失败，标记为"待人工协调"，不自动修正

## 8. 风险与边界

| 风险 | 描述 | 缓解措施 |
|------|------|----------|
| 约束规则误触发 | "推导"一词出现在非数学论文中，触发 mathematical_override | 规则添加置信度阈值 + 上下文窗口检查 |
| 视角爆炸 | 一个节点被添加过多视角 | 限制每个节点最多 8 个视角；相似视角合并 |
| 协调循环 | 发散建议添加视角，层级验证拒绝，发散再建议 | 单次协调最多 3 轮；人工介入终止循环 |
| 发散网络幻觉 | 子模块可能不存在于论文中 | 子模块标注 `mentioned` 字段；未提及的子模块降低置信度 |
| 模板覆盖不足 | 新领域论文无匹配模板 | 通用解构（generic deconstruct）兜底 + 人工添加模板 |
| 性能下降 | 多视角查询需要 JOIN 操作 | 预计算视角缓存；索引优化 |
