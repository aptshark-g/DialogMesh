## 问题一：领域识别完全依赖人工硬编码

### 现状

`thermal-vibration-coupling` 的键合图定义是手写死的，不是从节点 `content` 自动解析的。来一个全新论文节点，系统无法自动识别应该用哪个模板。

### 方案：语义映射→关键字解耦→链接分析分类器

**三层架构：**

```
输入：节点文本（标题+what+content）
  ↓
Layer 1: 语义嵌入粗筛（Sentence-BERT）
  - 将节点文本转为向量
  - 与预定义的「领域语义锚点」计算相似度
  - 输出：候选领域列表（Top 5）
  ↓
Layer 2: 关键字链接分析
  - 在候选领域内，提取文本中的关键术语
  - 构建术语共现网络，识别核心概念簇
  - 匹配领域模板的关键字规则
  - 输出：精确领域匹配 + 置信度
  ↓
Layer 3: LLM兜底
  - 若前两层置信度均 < 0.6
  - 调用LLM做开放式领域识别
  - Prompt: "请判断以下技术内容属于哪个工程领域..."
  - 输出：领域标签 + 置信度
```

**参考方案：**

| 方案 | 来源 | 核心思想 | 适用性 |
|------|------|---------|--------|
| **SciBERT/领域自适应嵌入** | Beltagy et al., 2019 | 在科学文献上预训练的BERT，术语理解优于通用模型 | 高 — 可直接加载预训练权重 |
| **关键词图+PageRank** | Mihalcea & Tarau, 2004 (TextRank) | 从文本构建术语共现图，用PageRank提取核心术语 | 高 — 零训练，纯算法 |
| **Few-shot领域分类** | Schick & Schütze, 2021 | 用LLM做少样本分类，无需微调 | 中 — 需设计好的Prompt |
| **知识图谱实体链接** | Shen et al., 2018 | 将文本术语链接到知识图谱实体，推断领域 | 中 — 需要领域KG |

**推荐组合：** Sentence-BERT粗筛 + TextRank关键词提取 + 规则匹配。LLM仅在置信度<0.6时兜底。

### 实施计划

| 阶段 | 任务 | 时间 |
|------|------|------|
| 1 | 加载SciBERT模型，生成领域语义锚点向量 | 半天 |
| 2 | 实现TextRank关键词提取 | 半天 |
| 3 | 构建30+领域的关键字规则库 | 2天 |
| 4 | 集成LLM兜底 + 置信度阈值调优 | 1天 |

## 问题二：键合图物理约束在转译中丢失

### 现状

0-节点的"势相等"、1-节点的"流相等"、功率守恒等物理约束，在函数树中变成了不可计算的文字字符串。

### 方案对比

| 维度 | 方案A：维持现状 | 方案B：约束节点（推荐） | 方案C：端口变量绑定 |
|------|--------------|---------------------|------------------|
| **核心思想** | 约束=自然文字 | 新增约束节点作为一等实体 | 端口级变量绑定+约束求解 |
| **改造范围** | 无 | 中度：补约束节点类型 | 深度：重构整个函数树 |
| **WL兼容** | 差 | 好：约束节点参与着色 | 好：变量绑定作为边特征 |
| **可计算性** | 无 | 中：约束公式可解析 | 高：可直接做数值校验 |
| **实施成本** | 0 | 2-3天 | 1-2周 |
| **适用场景** | 快速原型 | 工程落地（推荐） | 定量仿真需求 |

### 推荐方案B：约束节点（投入产出比最高）

**核心改造：**

```python
# 改造后的函数树节点类型
NODE_TYPES = {
    "function": "功能元件（R/C/I/Se/Sf/控制器/滤波器）",
    "constraint_0": "0-节点约束：势相等+流守恒",
    "constraint_1": "1-节点约束：流相等+势守恒", 
    "constraint_power": "功率守恒约束",
    "constraint_generic": "通用约束（自定义公式）",
}
```

**标准化映射规则：**

```
键合图0-节点 → constraint_0 节点
  ├── 内置硬约束1: e₁ = e₂ = ... = eₙ
  ├── 内置硬约束2: Σfᵢ = 0（带功率方向符号）
  └── 派生属性: ΣP = e × Σf = 0

键合图1-节点 → constraint_1 节点
  ├── 内置硬约束1: f₁ = f₂ = ... = fₙ
  ├── 内置硬约束2: Σeᵢ = 0（带功率方向符号）
  └── 派生属性: ΣP = f × Σe = 0
```

**改造后示例：**

```
热接触模块
└── 约束节点：J0_thermal (constraint_0)
    ├── 内置约束: e_ambient = e_R; f_ambient + f_R = 0
    ├── 关联子函数: T_ambient (Se) → 势端口接入J0
    └── 关联子函数: R_thermal_contact (R) → 势端口接入J0
```

**效果：**
- WL测试可直接读取约束节点公式
- 自动校验"同0节点的势变量赋值是否一致"
- 主动发现物理矛盾（如两个R元件接在同一0节点但势不相等）

## 问题三：WL颜色碰撞——同类型不同物理意义的元件无法区分

### 现状

`R_thermal_contact`（热阻）和 `R_damping`（机械阻尼）都是 `R` 类型，WL给它们相同颜色。但一个耗散热能，一个耗散机械能，物理意义完全不同。

### 根因分析

不是WL算法不够强，是**输入给WL的节点特征完全缺失物理语义信息**。好比两个人都叫"张三"，你只靠名字和社交关系区分，永远分不出哪个是医生、哪个是老师。

### 方案：节点特征工程（最低成本根治）

**改造前WL着色输入：**
```
hash([节点类型, 邻居类型集合])
# 热阻 → hash(["R", {"C", "Se"}]) = 颜色A
# 机械阻尼 → hash(["R", {"C", "Sf"}]) = 颜色A（碰撞！）
```

**改造后WL着色输入：**
```
hash([节点类型, 物理域, 能量属性, 势量纲, 流量纲, 邻居类型集合])
# 热阻 → hash(["R", "thermal", "dissipation", "temperature", "heat_flow", {"C", "Se"}]) = 颜色A
# 机械阻尼 → hash(["R", "mechanical", "dissipation", "force", "velocity", {"C", "Sf"}]) = 颜色B（不碰撞！）
```

**实施量：** 仅需修改WL的哈希函数输入字段，几行代码。

**更严谨的补充：加入量纲特征**

| 元件 | 物理域 | 能量属性 | 势量纲 | 流量纲 |
|------|--------|---------|--------|--------|
| 热阻 | thermal | dissipation | temperature (K) | heat_flow_rate (W) |
| 机械阻尼 | mechanical | dissipation | force (N) | velocity (m/s) |
| 热容 | thermal | storage | temperature (K) | heat_flow_rate (W) |
| 弹簧柔度 | mechanical | storage | force (N) | velocity (m/s) |
| 电气电阻 | electrical | dissipation | voltage (V) | current (A) |
| 电气电容 | electrical | storage | voltage (V) | current (A) |

**附加优化：带边特征的WL**

把连接边的语义（功率方向、量纲转换关系）也加入哈希，进一步提升区分度，复杂度几乎不增长。

## 问题四：从非结构化文本自动提取函数树

### 现状

控制系统的函数树是人工根据已知知识手写的。如果节点只有一段论文摘要，系统无法自动识别"这是控制系统"，更无法自动提取子函数结构。

### 方案：LLM+模板匹配（不是纯生成，也不是纯规则）

**工业界共识：** 大模型的核心价值是"语义理解"，不是"自由创作"。结构化输出必须用模板和规则约束。

**三层落地架构：**

```
核心资产层：标准函数树模板库
├── 控制类：PID控制、状态观测器、FxLMS-ANC、滑模控制...
├── 热域类：热传导、热对流、热辐射、相变...
├── 机械类：质量-弹簧-阻尼、多体动力学、模态分析...
└── 每个模板包含：固定节点层级、预留参数槽位、默认约束规则

执行层：LLM只做两件事
├── 任务1：模板匹配 —— 从文本语义匹配最相似的模板
│   └── 粗筛：关键词快速缩小范围
│   └── 精排：LLM语义匹配确认
└── 任务2：槽位填充 —— 从文本提取参数填入模板
    └── 滤波器阶数 → "256阶FIR"中的256
    └── 步长系数 → "μ=0.001"中的0.001

兜底层：规则校验（100%可控，不需要LLM）
├── 结构校验：输出节点层级是否和模板完全一致
├── 格式校验：是否符合下游工具导入要求
└── 合理性校验：参数值是否在合理范围
```

**Prompt设计（关键）：**

```
你是一个工程系统结构化提取助手。你的任务是从技术文本中识别系统架构，
并匹配到标准模板。

规则：
1. 只能从以下模板列表中选择，禁止创建新模板：
   [模板列表...]
2. 输出必须严格匹配模板结构，禁止新增未定义的节点
3. 仅填充模板中标记为「[槽位]」的参数
4. 如果文本内容不匹配任何模板，返回 "NO_MATCH"，不要猜测

输入文本：
{论文摘要}

输出格式（JSON）：
{
  "matched_template": "模板ID",
  "confidence": 0.0-1.0,
  "filled_slots": {
    "slot_name": "提取的值"
  },
  "reasoning": "匹配理由（简短）"
}
```

**横向对比：**

| 维度 | 纯规则方案 | 纯LLM生成 | LLM+模板匹配（推荐） |
|------|----------|----------|-------------------|
| 准确率 | 低 | 中 | **高** |
| 幻觉率 | 无 | 高 | **极低** |
| 维护成本 | 极高 | 低 | **低** |
| 复用性 | 差 | 无 | **强** |
| 开发量 | 大 | 极小 | **中等** |
| 适合场景 | 格式100%固定文档 | 临时一次性 | **工程落地** |

**极简落地路径（1-2人周）：**

1. **第1步（0成本）：** 把已手写的函数树整理成第一批模板（单通道ANC=模板1）
2. **第2步（1人天）：** 写带Schema约束的Prompt，用LLM的Structured Output功能
3. **第3步（1人天）：** 加JSON格式校验，确保输出可直接导入函数树工具
4. **第4步（持续）：** 遇到无匹配模板的新系统，LLM生成初版→人工审核→加入模板库

## 问题五：同构判定标准不明确

### 现状

单一0~1相似度分数无法回答"算不算同构"——因为"拓扑同构"、"功能同构"、"物理同构"三个不同抽象层级的问题，被混进了同一个分数里。

### 根因

键合图方法论本身就是为跨域同构而生：不同物理域系统，只要键合图拓扑一致，微分方程数学结构完全相同。但"结构同构"≠"物理可复用"≠"功能等价"，这是三个独立的判定维度。

### 方案：三层同构标准（从松到严）

| 层级 | 名称 | 判定依据 | 适用场景 | 示例判定 |
|------|------|---------|---------|---------|
| **L1** | 拓扑同构 | 纯图论结构等价，忽略语义 | 结构分析、方程求解框架复用 | 速度反馈环 vs 温度反馈环 → **同构** |
| **L2** | 功能同构 | 功能语义等价（耗散/储能/源/调节） | 架构跨域复用、设计灵感迁移 | 热阻 vs 机械阻尼 → **同构**（都是耗散） |
| **L3** | 物理约束同构 | 物理域、量纲、约束方程全部匹配 | 仿真模型直接复用 | 热阻 vs 机械阻尼 → **不同构**（量纲不同） |

**实施改造：**

```python
# 单一分数 → 三层分数
def compute_similarity(tree_a, tree_b) -> dict:
    return {
        "topological": wl_similarity(tree_a, tree_b, level="type_only"),
        "functional": wl_similarity(tree_a, tree_b, level="type+domain+energy"),
        "physical": wl_similarity(tree_a, tree_b, level="type+domain+energy+dimension"),
    }

# 场景化判定（取消全局硬阈值）
def classify_isomorphism(similarity: dict, use_case: str) -> str:
    if use_case == "architecture_search":
        return "ISOMORPHIC" if similarity["functional"] >= 0.8 else "NOT_ISOMORPHIC"
    elif use_case == "model_reuse":
        return "ISOMORPHIC" if similarity["physical"] >= 0.9 else "NOT_ISOMORPHIC"
    elif use_case == "structural_analysis":
        return "ISOMORPHIC" if similarity["topological"] >= 0.95 else "NOT_ISOMORPHIC"
```

**输出示例：**

```
系统A: 单通道ANC（控制系统）
系统B: 热-振耦合（键合图）

判定结果:
  拓扑相似度: 0.72 → 结构部分相似
  功能相似度: 0.45 → 功能不同（反馈控制 vs 物理耦合）
  物理相似度: 0.12 → 物理不可复用

综合结论: 拓扑层面可借鉴结构思路，但功能和物理层面不可复用。
```

**LLM的正确定位：**

- ❌ 不能让LLM做同构最终判定（确定性规则问题，LLM会前后不一致）
- ✅ LLM做前置标注：给未标注节点自动打功能类型、物理域标签
- ✅ LLM做结果解释：把分层判定结果翻译成自然语言

## 问题六：缺少缓存和增量更新机制

### 现状

每次运行都重新转译和重新计算WL。1000节点时不可接受。

### 方案A：两级缓存（投入1人天，解决90%问题）——推荐

**第一级：图结构缓存**
- 缓存内容：邻接表、节点初始标签、边属性（WL可读的格式）
- 失效机制：内容哈希（节点属性+连接关系的哈希值）
- 命中时：跳过转译和建图，直接读缓存
- 收益：从"几百毫秒"降到"几毫秒"

**第二级：WL结果缓存**
- 缓存内容：最终着色向量、节点颜色映射、预计算相似度矩阵
- 失效机制：图结构哈希不变则直接返回
- 命中时：跳过WL计算
- 适用：多次运行WL测试、多次比对相似度

```python
class WLCached(SimpleWL):
    def __init__(self):
        self.graph_cache = {}  # hash → graph_structure
        self.wl_cache = {}     # hash → wl_result
    
    def compute_similarity(self, tree_a, tree_b):
        hash_a = self._compute_tree_hash(tree_a)
        hash_b = self._compute_tree_hash(tree_b)
        
        # 检查图结构缓存
        if hash_a not in self.graph_cache:
            self.graph_cache[hash_a] = self._build_graph(tree_a)
        
        # 检查WL结果缓存
        cache_key = f"{hash_a}::{hash_b}"
        if cache_key in self.wl_cache:
            return self.wl_cache[cache_key]
        
        # 未命中，计算并缓存
        result = super().compute_similarity(tree_a, tree_b)
        self.wl_cache[cache_key] = result
        return result
```

### 方案B：增量WL更新（投入3-5人天，解决局部修改场景）

**核心原理：** WL着色传播是局部的。一个节点标签变化，最多影响k跳邻居（k=WL迭代轮次）。

**更新逻辑：**

| 修改类型 | 更新范围 | 计算复杂度 |
|---------|---------|-----------|
| 修改单个节点属性 | 从该节点出发，重算3-5轮迭代 | O(Δ)，通常<10个节点 |
| 新增/删除一条边 | 更新两个端点的邻域，局部迭代 | O(Δ) |
| 新增/删除一个节点 | 更新其所有邻居的邻域 | O(Δ) |

**效果：** 从全量O(n)降到增量O(Δ)，亚毫秒级更新。

**推荐策略：** 先做方案A（1人天，收益90%），未来规模到万节点以上再做方案B。

## 一句话总结

**v5.2c 证明了"形式化转译→WL同构判定"的理论可行性，但暴露了从"原型"到"工程"的六道鸿沟。修复方案的核心原则是：不推翻现有架构，用最小改造成本解决最大瓶颈——节点特征工程半天根治WL碰撞，LLM+模板匹配2-3天打通自动提取，三层同构标准1天消除判定歧义。三道P0做完，形式化转译引擎就从"能跑"变成"能用"。**
